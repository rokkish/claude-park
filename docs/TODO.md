## ステージ追加の自動化

**目的**: ステージの実装と検証を、上位モデル（Opus）を使わずに回せるようにする。
いま Opus を要求しているのは「幾何の検算」と「詰み盤面の発見」の2点だけで、
どちらも機械化の余地があります。設計（気づきの発明）だけが残ります。

作業手順は [AUTHORING.md](AUTHORING.md)。

### 1. 到達力を実測付きの定数にする — `src/game/reach.ts`

単独62.5 / ブースト86.5 / 箱＋ブースト110.5 / 二段149 / 水平87 / 二段水平102 を
エクスポートし、**実際に物理を走らせて測るテスト**で裏を取る。
いまこれらは SPEC と設計者の記憶にしかなく、参照するたびに再計算している。

### 2. ステージ検査 — `scripts/check-stage.ts` ＋ 全ステージ共通テスト

機械判定できるものを全部自動化する。

- スポーンが床の上にあるか、ギミックがグリッド範囲内か
- `listen` しているチャンネルを誰かが `emit` しているか（配線の書き間違い）
- `goal.requires` の鍵が実在するか
- 板・ゲートが地形に埋まっていないか
- **面と面の縦・横の隙間を 1 の到達力と突き合わせた表**を出力する

（行の長さ・未知の文字・未登録の `type` は既にロード時に throw するので対象外）

### 3. テストヘルパ — `tests/helpers/stage.ts`

`newStage / standOn / rideOn / walkRight / expectCleared` を用意する。
いま各ステージのテストが毎回同じ土台を書き直していて、通しクリアテストが
高く付いている。ヘルパがあれば20行程度で書けるので、**受け入れ条件として
必須化できる**（＝2-2 型の詰み盤面を実装側で検出できる）。

### 4. プレビューの汎用化 — `scripts/preview-stage.ts`

ポーズをスクリプトにハードコードするのをやめ、`--place p1=8,15 --hold 150` の
ように引数で指定できるようにする。ステージを足すたびにスクリプトを編集している。
