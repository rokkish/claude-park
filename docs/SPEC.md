# Claude Park 仕様書 v0.1

Pico Park 風のローカル協力アクションパズル。キャラクターに Claude Code のマスコット **Clawd** を使う。

## 0. 決定事項サマリ

| 項目 | 決定 |
| --- | --- |
| 協力形式 | ローカル2人・1キーボード（P1=WASD, P2=矢印キー） |
| 技術スタック | TypeScript + Canvas2D 自作エンジン（ビルドは Vite） |
| Clawd の見た目 | コードによる手描き風ベクタ描画。差し替え可能な `CharacterSkin` 越し |
| PoC 範囲 | 1ステージ・4ギミック種で「協力しないとクリア不能」を成立させる |
| 実行環境 | モダンブラウザ（Chrome/Firefox/Safari 最新）、`npm run dev` で起動 |

要求との対応:

- 要求1（Clawd を使う）→ §6 キャラクター表現
- 要求2（1ステージで PoC）→ §7 ステージ1設計
- 要求3（ギミック・ステージを追加しやすい設計）→ §4 シグナル方式、§5 ギミック登録、§8 拡張手順
- 要求4（ブラウザで遊べる）→ §1 構成、§9 マイルストーン

## 2. ゲームループと入力

### 2.1 固定タイムステップ

物理を安定させるため、シミュレーションは **固定 1/60 秒**。描画は requestAnimationFrame。

```
accumulator += min(realDelta, 0.25)   // スパイク時のスパイラルを防ぐ上限
while (accumulator >= DT) { step(DT); accumulator -= DT }
render()
```

補間は行わない（60Hz 固定で十分滑らか。PoC の複雑さを増やさない）。

### 2.2 入力

| | 左 | 右 | ジャンプ |
| --- | --- | --- | --- |
| P1 | `A` | `D` | `W` / `Space` |
| P2 | `←` | `→` | `↑` |

共通キー: `R` = ステージリセット、`Enter` = タイトルから開始。

`input.ts` は「押下中フラグ」ではなく **`{ left, right, jumpHeld, jumpPressed }`** を返す。`jumpPressed` は「このステップで新たに押された」エッジ。keydown は自動リピートするため、`repeat` フラグを見て弾く。

キーマップは `KeyMap[]` の配列として定義し、プレイヤー数を増やす場合はエントリを足すだけにする（将来の Gamepad API 追加も、`InputSource` インターフェースを実装した別実装を差し込むだけで済ませる）。

## 3. 物理

Pico Park の肝は **プレイヤーがプレイヤーの上に乗れること**。ここが崩れるとゲームが成立しないので、最初に正しく作る。

### 3.1 Actor / Solid モデル

Celeste / TowerFall で使われる方式を採る。

- **Solid**: 他者を押しのける存在。タイル壁、動く床、ゲート。
- **Actor**: 環境に押される存在。プレイヤー、押せる箱。
- **プレイヤーは Actor であり、同時に他プレイヤーにとっての Solid でもある**（頭に乗れる）。

### 3.2 移動と衝突解決

すべての AABB は軸平行矩形。移動は **X → Y の順に分離** して解決する（斜め衝突の破綻を防ぐ定石）。

サブピクセル残差を `xRemainder` / `yRemainder` に持ち、整数ピクセル単位で 1px ずつ進めながら衝突判定する。これにより高速移動時のトンネリングが原理的に起きない。

```
moveX(amount):
  xRemainder += amount
  move = round(xRemainder); xRemainder -= move
  step = sign(move)
  while move != 0:
    if collidesAt(x + step, y): onCollideX(); break
    x += step; move -= step
```

`collidesAt` が見るもの:

- タイルグリッド（`#` = solid）
- 他プレイヤーの AABB
- Solid を持つギミック（閉じたゲートなど）

### 3.3 プレイヤー同士の衝突

そのまま「硬い壁」にすると、地上で並んだときに互いに詰まって身動きが取れなくなる。以下で分ける。

- **縦方向**: 硬い。落下中に相手の頭上に接地でき、下から突き上げると乗っている相手が持ち上がる。
- **横方向**: **押し合い**。A が B にぶつかったら、A の残り移動量を B に伝播させて B を押す。B が壁で詰まっている場合のみ A も止まる。伝播は最大4段まで（無限再帰を防ぎつつ、3人以上が横に並んでも押せる長さ）。

### 3.4 ライダー搬送（乗っている相手を運ぶ）

Solid（動く床、および「他プレイヤーの頭」）が動くとき、その上に乗っている Actor を同じ量だけ動かす。これがないと、乗った瞬間に足元が置き去りになって滑り落ちる。

実装状況: **Actor 同士（頭の上に乗る）と、ギミック由来の Solid（動く床）の両方に対応済み**。
当初は Actor 同士しか実装しておらず、床を動かすとプレイヤーをすり抜けて圧殺していた。

- **ライダー判定**: `actor.bottom == solid.top` かつ X 方向にオーバーラップ。
- **処理順**: 乗っている関係を有向グラフとみなし、**下から上へトポロジカル順**に更新する。3人以上の塔でも破綻しない。相互に乗っている循環は物理的にあり得ないが、防御的に検出したら循環を切る。
- 運ばれた先が壁だった場合、Actor は運搬を諦めて相手の頭から滑り落ちる（挟まって固まるより良い）。

**ギミック由来の Solid が動く場合** は、ギミックが `solidDelta?(): {dx, dy}` で動いた量を申告する。
前フレームとの差分を物理側で推測する手もあるが、ステージのリセットによる瞬間移動と区別できないので
採らない。動かした本人が量を知っている。実装しないギミックには一切コストが掛からない（§5.1 の能力表明）。

処理は Actor が自分で動き出す**前**に行う。後にすると足場の上のプレイヤーが1フレームぶん置き去りに
なって滑る。順序は次の通り:

1. 乗員を「**動く前の**位置」で確定する。box は既にギミックが動かした後なので、動いた後に数えると
   置き去りにされた乗員を拾えない
2. その Solid を一時的に障害物から外す（外さないと、めり込んだ Actor が自分の中から出られない）
3. 重なった Actor を進行方向へ、めり込みぶん押し出す
4. 押し出していない乗員を、動いた量だけ運ぶ
5. 障害物から外したのを戻す（**必ず finally で**。抜けたまま残るとその Solid は以後ずっと素通りになる）

押し出した相手は既に動いているので、乗員としては運ばない。両方効くと2倍動いてしまう
（上昇する足場の上に乗っている場合がまさにこれ）。

### 3.5 圧殺

Solid（閉じるゲート）と壁の間に挟まれた Actor は「圧殺」とし、そのプレイヤーだけスポーン地点に復帰させる。ステージ全体のリセットにはしない（理不尽さを避ける）。

### 3.6 チューニング定数（`tuning.ts`）

単位は px / 秒。タイル = 24px、プレイヤー = 20w × 24h。

| 定数 | 値 | 意図 |
| --- | --- | --- |
| `GRAVITY` | 2000 | |
| `MAX_FALL` | 700 | |
| `RUN_SPEED` | 160 | 約 6.7 タイル/秒 |
| `RUN_ACCEL` | 1200 | |
| `GROUND_FRICTION` | 1600 | |
| `AIR_FRICTION` | 400 | 空中でも多少は制御できる |
| `JUMP_VELOCITY` | 500 | |
| `JUMP_CUT_MUL` | 0.4 | ボタンを離すと上昇を減衰＝可変ジャンプ |
| `COYOTE_TIME` | 0.08 | 崖から落ちた直後もジャンプ可 |
| `JUMP_BUFFER` | 0.10 | 着地直前の入力を拾う |

**この数値が設計上の意味を持つ**:

- 単独ジャンプの到達高 = `JUMP_VELOCITY² / (2 × GRAVITY)` = **62.5px ≒ 2.6 タイル**
- 相手の頭（+24px = 1タイル）に乗ってからのジャンプ = **86.5px ≒ 3.6 タイル**

よって **高さ3タイルの段差は「単独では絶対に無理／2人なら余裕を持って届く」** 境界になる。ステージ1はこの境界の上に成立している。ここを変えるとステージ設計が破綻するので、変更時は §7 の検算も併せて更新すること。

## 4. シグナルシステム（拡張性の中核）

ギミック同士を直接参照させると、「板を押したら扉が開く」ために板が扉を知る必要が生じ、組み合わせが増えるたびに配線が爆発する。これを **名前付きチャンネル** で完全に分離する。

```ts
class SignalBus {
  private channels = new Map<string, number>();
  set(name: string, value: number | boolean): void;
  get(name: string): number;            // 未定義は 0
  isOn(name: string): boolean;          // != 0
  clearFrame(): void;                   // 毎ステップ先頭で「瞬間型」をリセット
}
```

- **発信側**（感圧板、レバー、スイッチ）は自分が知っているチャンネル名に値を書くだけ。受信側の存在を知らない。
- **受信側**（ゲート、リフト、消える床）はチャンネル名のリストと結合モードだけを持つ。発信側の種類を知らない。

結合モードは式パーサを作らず、以下の3つで十分:

| mode | 意味 |
| --- | --- |
| `all` | 全チャンネルが ON（デフォルト） |
| `any` | いずれかが ON |
| `none` | すべて OFF（＝反転ゲート） |

これにより **「新しいスイッチ」を作っても既存の全受信側が自動的に対応し、「新しい受信ギミック」を作っても既存の全スイッチが自動的に使える**。組み合わせ爆発が起きない。

`latch: true` オプションを受信側に持たせると、一度 ON になったら戻らない（PoC では未使用だが、鍵付き扉などで効く）。

## 5. ギミックのインターフェース

### 5.1 定義

必須メソッドを最小にし、能力はオプショナルメソッドで表明する（Capability 方式）。実装しなければそのコストは一切かからない。

```ts
export interface GimmickContext {
  signals: SignalBus;
  stage: Stage;
  players: Player[];
  requestClear(): void;              // ゴールが呼ぶ
}

export interface Gimmick {
  readonly type: string;
  readonly aabb: AABB;               // 判定・描画の基準矩形

  update(dt: number, ctx: GimmickContext): void;
  draw(r: Renderer): void;

  /** 実装すると Solid になる。null を返す間はすり抜ける（開いたゲート） */
  solidAABB?(): AABB | null;
  /** 実装すると重なり検知が来る（感圧板、鍵、ゴール、トゲ） */
  onOverlap?(player: Player, ctx: GimmickContext): void;
  /** ステージリセット時の初期化 */
  reset?(): void;
}

export interface GimmickDef<P = any> {
  type: string;
  create(params: P & { x: number; y: number }, stage: Stage): Gimmick;
}
```

### 5.2 登録簿

```ts
// registry.ts
const defs = new Map<string, GimmickDef>();
export function registerGimmick(def: GimmickDef) { defs.set(def.type, def); }
export function createGimmick(type: string, params: any, stage: Stage): Gimmick {
  const def = defs.get(type);
  if (!def) throw new Error(`未登録のギミック type: "${type}"`);
  return def.create(params, stage);
}
```

```ts
// gimmicks/index.ts —— ギミックを追加したらここに1行足すだけ
import { plateDef } from "./plate";
import { gateDef } from "./gate";
import { keyDef } from "./key";
import { goalDef } from "./goal";

[plateDef, gateDef, keyDef, goalDef].forEach(registerGimmick);
```

未登録の type を含む JSON は**ロード時に即エラー**にする（プレイ中に静かに消えるより、開発時に気付ける方がよい）。

### 5.3 更新順序（1ステップの処理順）

順序が曖昧だと、シグナルが受信側に届かないバグの温床になる。以下に固定する。

1. 入力サンプリング
2. プレイヤーの速度更新（重力・加速・ジャンプ）
3. ギミック `update()` — Solid の開閉・移動と**受信側の評価**はここ
4. ギミック由来の Solid 集合を物理へ反映
5. プレイヤーの `moveX()` → `moveY()`（ライダー搬送はこの中で完結）、接地・圧殺判定
6. **`signals.clearFrame()`**
7. 重なり判定 → 該当ギミックの `onOverlap()`（**感圧板がシグナルを立てるのはここ**）

**`clearFrame()` の位置が最重要**。これをステップ先頭に置くと、前ステップの手順7で発信側が立てた値を、受信側（手順3）が読む前に消してしまい、**感圧板の信号がゲートに一度も届かない**。実装初回にこの順序を誤って踏み抜いたので、変更するときは `tests/stage01.test.ts` の「板に乗るとゲートの Solid が消え、降りると戻る」で必ず検証すること。

この順序では、板を踏んでから扉が通れるようになるまで 1 フレーム（16ms）の遅れが出る。知覚できない差であり、扉が開いた瞬間にプレイヤーが押し出されて挟まる事故が起きない利点の方が大きい。

## 6. キャラクター表現（Clawd）

### 6.1 方針

Clawd の公式アセットは手元にないため、**Anthropic のクレイオレンジ `#D97757` を基調に、Clawd 的なシルエットをコードで描く**。ドット絵ではなくベクタ（`ctx.arc` / `quadraticCurveTo`）で描くので、拡大しても滑らか。

差し替えを前提にインターフェースを切る:

```ts
export interface CharacterSkin {
  draw(r: Renderer, s: CharacterState): void;
}
export interface CharacterState {
  x: number; y: number; w: number; h: number;
  facing: 1 | -1;
  vx: number; vy: number;
  grounded: boolean;
  squash: number;     // 1 = 通常, <1 = 潰れ, >1 = 伸び
  carrying: boolean;  // 頭に誰か乗っている
  color: PlayerPalette;
}
```

`ClawdSkin implements CharacterSkin` として実装。将来スプライトシートを使う場合は `SpriteSkin` を作って差し替えるだけで、ゲームロジックは無変更。

### 6.2 見た目の要素

- 丸みのあるずんぐりした胴体。上部に短いアンテナ/触角が1本。
- 目は大きめの単純なドット2つ。進行方向（`facing`）に寄せる。
- **スカッシュ＆ストレッチ**: ジャンプ踏切で縦に伸び、着地で横に潰れる。`squash` は着地時に 0.7 へ落として毎ステップ 1.0 へ指数回復させる。この1要素だけで「生きている感じ」が跳ね上がるので PoC でも省かない。
- **表情の変化**: 空中では目を少し大きく、頭に相手が乗っている（`carrying`）ときは踏ん張った目にする。協力ゲームなので「乗せられている」ことが一目で分かるのが重要。
- 接地時のわずかな上下バウンス（呼吸）。

### 6.3 2人の識別

P1 = クレイオレンジ `#D97757`、P2 = 同じ形で色相をずらした青緑 `#57A8D9`。形は完全に同じ Clawd で、色だけが違う。足元に自機カラーの小さな影を落として、重なったときも判別できるようにする。

## 7. ステージ1「Boost & Hold」

### 7.1 教えたいこと

1. **相手の頭に乗れば届く**（単独では絶対に届かない段差）
2. **片方が留まって、片方が進む**（感圧板とゲート＝役割の非対称性）
3. **役割は入れ替わる**（乗せた側が最後に自力で合流する）

「2人いないとクリア不能」であることが PoC の証明対象なので、単独攻略ルートが存在しないことを設計と数値の両方で保証する。

### 7.2 レイアウト

40 × 18 タイル。`#` = 壁、`.` = 空。

```

y=1   #......................................#
y=2   #......................................#
y=3   #......................................#
y=4   #......................................#
y=5   #......................................#
y=6   #......................................#
y=7   #......................................#
y=8   #......................................#
y=9   #......................................#
y=10  #......................................#
y=11  #......................................#
y=12  #......................................#
y=13  #............######....................#
y=14  #......................................#
y=15  #......................................#
y=16  ########################################
y=17  ########################################
      0123456789...
```

- 地面 = y=16 の上面（`y_px = 384`）
- **棚 + 仕切り壁** = x=13〜18 の y=13（`y_px = 312`、地面から **3タイル = 72px**）
- ゲート（ギミック）が x=18 の y=14〜15 を塞ぐ。閉じている間、地上からエリアAとBは行き来できない
- 棚の上（y=13 の上面）は x=13 から x=18 まで連続しており、**x=18 から右に歩けばエリアBへ落ちられる**

エリアA = x=1〜17（スタート地点）、エリアB = x=19〜38（鍵とゴール）。

| P2 スポーン | (7, 15) | |
| 感圧板 `plate` | (15, 12) w=2 | `emit: "sw1"` |
| ゲート `gate` | (18, 14) h=2 | `listen: ["sw1"], mode: "all"` |
| 鍵 `key` | (25, 15) | `id: "key1"` |
| ゴール `goal` | (35, 15) w=3 | `requires: ["key1"], needAllPlayers: true` |

### 7.4 想定解法

1. P1 が棚の左下（x≈12）に立つ。P2 が P1 の頭に飛び乗る。
2. P2 が頭の上からジャンプして棚（y=13）に上がる。
3. P2 が棚の上の感圧板 (15,12) に乗る → `sw1` が ON → x=18 のゲートが開く。
4. P1 が地上を右に歩き、開いたゲートを抜けてエリアBへ。
5. P2 が板から降りる（ゲートは閉じるが、P1 はもう向こう側）。P2 は棚を右端まで歩き、x=18 から**エリアBへ落下**して合流。
6. P1 が鍵 (25,15) を回収。
7. 2人ともゴール (35〜37, 15) に入る → クリア。

### 7.5 単独攻略が不可能であることの検算

| 経路 | 必要高さ | 単独の到達 | 判定 |
| --- | --- | --- | --- |
| 地上から棚 (y=13) に登る | 72px（3タイル） | 62.5px | **不可**（9.5px 不足） |
| 地上から仕切り壁 x=18 を越える | 72px | 62.5px | **不可** |
| 頭に乗ってから棚に登る | 72px | 24 + 62.5 = 86.5px | 可（14.5px 余裕） |
| 頭に乗った位置から棚まで | 48px | 62.5px | 可 |

単独では棚にも仕切り壁にも登れず、ゲートを開ける感圧板は棚の上にしかない。**エリアBへ到達する経路が物理的に存在しない**。

余裕 14.5px は「シビアすぎず、しかし偶然できてしまうこともない」量。`JUMP_VELOCITY` を変更する場合はこの表を再計算すること。

### 7.6 失敗と復帰

- 手順3〜5の順序を間違えると（P2 が板に乗らずに先へ落ちる）、P1 が取り残されて詰む。**これは意図した失敗**で、協力の必要性を体感させる。
- `R` キーで即リセット。詰み検出は実装しない（プレイヤーが自分で気付いて押す方が学習になり、実装も単純）。

### 7.8 ワールド1「スイッチ（押している間だけ効く）」

ステージを1本ずつではなく、**1つの学習テーマ = 1ワールド**でまとめる（Pico Park 本家の構成に倣う）。ワールド1のテーマは「スイッチは押している間だけ効く」。3ステージで、このテーマの異なる側面を1つずつ教える。

| ステージ | 名前 | 教える側面 |
| --- | --- | --- |
| 1-1 | Boost & Hold | 相手の頭に乗れば届く／片方が留まり片方が進む（§7 で詳説済み） |
| 1-2 | Both at Once | **2枚のスイッチを同時に**押さないと開かない＝両者とも同時に別の場所を占有するので、開いた瞬間だけ自由になる。だからゲートは `latch: true` で開いたら戻らない必要がある |
| 1-3 | Bridge | スイッチが「開ける」のではなく**閉じたときだけ通れる床**を作る（`mode: "none"` の反転ゲート）。1-1・1-2とは逆に「押されている間だけ実体化する」経験をさせ、2枚の板を**役割交代でリレー**する |

3ステージとも既存ギミック（`plate` / `gate` / `key` / `goal`）の組み合わせだけで作られており、ギミックのコードは1行も追加していない（§8.2 の想定どおり）。

ワールドは現状1つしかないため、`StageData` に `world` フィールドはまだ足していない。ステージ番号の「1-」部分は `game.ts` の HUD 描画側で固定値として持たせている。第2ワールドを作るときに `StageData` へ `world: number` を追加し、そちらから取るように直す。

### 7.9 ステージ1-2「Both at Once」の検算

`src/stages/stage-02.json`。レイアウトはステージ1と同じ 40×18 タイルで、地面（y_px=384）の右手前（タイル28）に、床から天井まで完全に塞ぐ縦の壁＋ゲートがある。棚（タイル17〜22, y=13, 地面から3タイル=72px）はステージ1と同じ理由で単独では登れない。

| 要素 | 位置 | 役割 |
| --- | --- | --- |
| 板A `swA` | 地上 (4, 15) | 地上に残った側が踏む |
| 板B `swB` | 棚の上 (19, 12) | ブーストされた側が踏む |
| ゲート | (28, 14) h=2, `listen: ["swA","swB"]`, `mode: "all"`, `latch: true` | 縦の壁（列28, 行1〜13が地形として常時Solid）＋ゲート（行14〜15）で床から天井まで塞ぐ |

**単独攻略が不可能であることの検算**:

| 経路 | 必要高さ / 条件 | 単独の到達 | 判定 |
| --- | --- | --- | --- |
| 地上から棚 (y=13) へ登る | 72px（3タイル） | 62.5px | **不可**（9.5px不足） |
| 板Aと板Bを同時に踏む | 2箇所を同時に占有 | 1人は1箇所にしか居られない | **不可**（棚に登れる／登れないに関係なく、そもそも1人では成立しない条件） |

棚に登れないので板Bへ単独で到達できず、たとえ登れたとしても板Aと板Bを同時に踏むことは1人の体では不可能。**`mode: "all"` の2チャンネル同時条件が、この不可能性の核**。

**`latch: true` が必須である理由**: 両方を同時に踏めるのは「地上の1人」と「棚の1人」が別々に配置されているこの一瞬だけで、ゲートが開いた次の瞬間には少なくとも片方が板から離れて移動を始める（でないとゴールへ辿り着けない）。`latch` が無ければ、板から足が離れた時点でゲートが再び閉じ、抜けている途中のプレイヤーを挟んでしまう。ステージ1のゲートは `latch` 不使用（板の上から動かないので閉じても困らない）だが、このステージでは`latch`が無いと物理的にクリア不能になる。`tests/stage02.test.ts` の「ラッチ」テストで固定している。

### 7.10 ステージ1-3「Bridge」の検算

`src/stages/stage-03.json`。40×18タイル、床面はどこも y=13（y_px=312）で統一されている１部屋。中央のタイル18〜23（幅6タイル=144px）だけ床が無い谷で、その下はグリッド外＝谷底（y_px=432、床面から120px＝5タイル）まで落ちる。

| 要素 | 位置 | 役割 |
| --- | --- | --- |
| 板1 | (12, 12) | 谷の手前側（近い方） |
| 板2 | (26, 12) | 谷の対岸側（遠い方） |
| 橋（ゲート） | (18, 13) w=6 h=1, `listen: ["sw1"]`, `mode: "none"` | 板1・板2は**同じチャンネル `sw1`** を鳴らす。反転ゲートなので、押されているあいだ**閉じる＝橋として実体化する** |

**単独攻略が不可能であることの検算**:

| 経路 | 必要距離 / 高さ | 単独の到達 | 判定 |
| --- | --- | --- | --- |
| 谷を跳び越える | 144px（6タイル） | 最大水平到達距離 約87px（3.63タイル） | **不可**（約57px不足） |
| 谷底から地上へ登り返す | 120px（5タイル） | 単独62.5px／頭に乗っても86.5px | **不可**（頭に乗っても33.5px不足） |

跳躍では届かず、誤って落ちても登り返せない（しかも登り返すには落ちた側にもう1人が要るが、そもそもここに来られるのは2人揃っている場合だけ）。橋を実体化させるには常にどちらかの板の上に誰かがいなければならないので、**2人が近い板／遠い板を交代で踏みながら渡るリレー**以外にクリア経路が無い。`tests/stage03.test.ts` の「谷は単独では渡れない」「受け渡しで渡れる」で固定している。

板1・板2が別チャンネルではなく**同じ `sw1`** を共有している点が肝で、これにより「Aが手前で踏み続ける→Bが渡る→Bが対岸の板に乗り換える→Aが渡る」という**受け渡し**が可能になる（別チャンネルにして `mode: "any"` にしても橋の開閉自体は同じ結果になるが、「どちらの板でも同じ橋が出る」という設計意図を1チャンネルの方が素直に表せるため、こちらを採用している）。
