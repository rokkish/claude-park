# Claude Park 仕様書 v0.1

Pico Park 風のローカル協力アクションパズル。キャラクターに Claude Code のマスコット **Clawd** を使う。

## 0. 決定事項サマリ

| 項目 | 決定 |
| --- | --- |
| 協力形式 | ローカル2人・1キーボード（P1=WASD, P2=矢印キー） |
| 技術スタック | TypeScript + Canvas2D 自作エンジン（ビルドは Vite） |
| Clawd の見た目 | コードによる手描き風ベクタ描画。差し替え可能な `CharacterSkin` 越し |
| PoC 範囲 | 1ステージ・4ギミック種で「協力しないとクリア不能」を成立させる |
| 実行環境 | モダンブラウザ（Chrome/Firefox/Safari 最新）、`npm run dev` で起動 |

要求との対応:

- 要求1（Clawd を使う）→ §6 キャラクター表現
- 要求2（1ステージで PoC）→ §7 ステージ1設計
- 要求3（ギミック・ステージを追加しやすい設計）→ §4 シグナル方式、§5 ギミック登録、§8 拡張手順
- 要求4（ブラウザで遊べる）→ §1 構成、§9 マイルストーン

### 1.2 画面

- 論理解像度 **960 × 432 px**（24px タイル × 40 × 18）。
- **カメラ**は `engine/camera.ts` の平行移動と拡大縮小だけで、描画の先頭で1回かける。ステージが画面に収まるなら全体を等倍で表示（1-1〜4-2 の 40×18 はこれ）。画面より大きいステージでは**2人を囲む範囲を追う**: 余白 96px を取った範囲が収まる最大の倍率（上限は等倍）で中心を追い、2人が離れるほど引きになる。ステージの端より外は映さない。毎フレーム目標へ 8/秒の割合で寄せ、やり直しとステージ切替では補間せずに飛ぶ。画面の端は当たり判定ではないので、物理はカメラを知らない。
- Canvas は論理解像度で描画し、CSS で viewport に合わせて等比拡大（`object-fit: contain` 相当）。
- `devicePixelRatio` を見て backing store を拡大し、高 DPI でも Clawd の曲線が滑らかに出るようにする。

## 2. ゲームループと入力

### 2.1 固定タイムステップ

物理を安定させるため、シミュレーションは **固定 1/60 秒**。描画は requestAnimationFrame。

```
accumulator += min(realDelta, 0.25)   // スパイク時のスパイラルを防ぐ上限
while (accumulator >= DT) { step(DT); accumulator -= DT }
render()
```

補間は行わない（60Hz 固定で十分滑らか。PoC の複雑さを増やさない）。

### 2.2 入力

| | 左 | 右 | ジャンプ |
| --- | --- | --- | --- |
| P1 | `A` | `D` | `W` / `Space` |
| P2 | `←` | `→` | `↑` |

共通キー: `R` = ステージリセット、`Enter` = タイトルから開始。

`input.ts` は「押下中フラグ」ではなく **`{ left, right, jumpHeld, jumpPressed }`** を返す。`jumpPressed` は「このステップで新たに押された」エッジ。keydown は自動リピートするため、`repeat` フラグを見て弾く。

キーマップは `KeyMap[]` の配列として定義し、プレイヤー数を増やす場合はエントリを足すだけにする（将来の Gamepad API 追加も、`InputSource` インターフェースを実装した別実装を差し込むだけで済ませる）。

## 3. 物理

Pico Park の肝は **プレイヤーがプレイヤーの上に乗れること**。ここが崩れるとゲームが成立しないので、最初に正しく作る。

### 3.1 Actor / Solid モデル

Celeste / TowerFall で使われる方式を採る。

- **Solid**: 他者を押しのける存在。タイル壁、動く床、ゲート。
- **Actor**: 環境に押される存在。プレイヤー、押せる箱。
- **プレイヤーは Actor であり、同時に他プレイヤーにとっての Solid でもある**（頭に乗れる）。

### 3.2 移動と衝突解決

すべての AABB は軸平行矩形。移動は **X → Y の順に分離** して解決する（斜め衝突の破綻を防ぐ定石）。

サブピクセル残差を `xRemainder` / `yRemainder` に持ち、整数ピクセル単位で 1px ずつ進めながら衝突判定する。これにより高速移動時のトンネリングが原理的に起きない。

```
moveX(amount):
  xRemainder += amount
  move = round(xRemainder); xRemainder -= move
  step = sign(move)
  while move != 0:
    if collidesAt(x + step, y): onCollideX(); break
    x += step; move -= step
```

`collidesAt` が見るもの:

- タイルグリッド（`#` = solid）
- 他プレイヤーの AABB
- Solid を持つギミック（閉じたゲートなど）

### 3.3 プレイヤー同士の衝突

そのまま「硬い壁」にすると、地上で並んだときに互いに詰まって身動きが取れなくなる。以下で分ける。

- **縦方向**: 硬い。落下中に相手の頭上に接地でき、下から突き上げると乗っている相手が持ち上がる。
- **横方向**: **押し合い**。A が B にぶつかったら、A の残り移動量を B に伝播させて B を押す。B が壁で詰まっている場合のみ A も止まる。伝播は最大4段まで（無限再帰を防ぎつつ、3人以上が横に並んでも押せる長さ）。

### 3.4 ライダー搬送（乗っている相手を運ぶ）

Solid（動く床、および「他プレイヤーの頭」）が動くとき、その上に乗っている Actor を同じ量だけ動かす。これがないと、乗った瞬間に足元が置き去りになって滑り落ちる。

実装状況: **Actor 同士（頭の上に乗る）と、ギミック由来の Solid（動く床）の両方に対応済み**。
当初は Actor 同士しか実装しておらず、床を動かすとプレイヤーをすり抜けて圧殺していた。

- **ライダー判定**: `actor.bottom == solid.top` かつ X 方向にオーバーラップ。
- **処理順**: 乗っている関係を有向グラフとみなし、**下から上へトポロジカル順**に更新する。3人以上の塔でも破綻しない。相互に乗っている循環は物理的にあり得ないが、防御的に検出したら循環を切る。
- 運ばれた先が壁だった場合、Actor は運搬を諦めて相手の頭から滑り落ちる（挟まって固まるより良い）。

**ギミック由来の Solid が動く場合** は、ギミックが `solidDelta?(): {dx, dy}` で動いた量を申告する。
前フレームとの差分を物理側で推測する手もあるが、ステージのリセットによる瞬間移動と区別できないので
採らない。動かした本人が量を知っている。実装しないギミックには一切コストが掛からない（§5.1 の能力表明）。

処理は Actor が自分で動き出す**前**に行う。後にすると足場の上のプレイヤーが1フレームぶん置き去りに
なって滑る。順序は次の通り:

1. 乗員を「**動く前の**位置」で確定する。box は既にギミックが動かした後なので、動いた後に数えると
   置き去りにされた乗員を拾えない
2. その Solid を一時的に障害物から外す（外さないと、めり込んだ Actor が自分の中から出られない）
3. 重なった Actor を進行方向へ、めり込みぶん押し出す
4. 押し出していない乗員を、動いた量だけ運ぶ
5. 障害物から外したのを戻す（**必ず finally で**。抜けたまま残るとその Solid は以後ずっと素通りになる）

押し出した相手は既に動いているので、乗員としては運ばない。両方効くと2倍動いてしまう
（上昇する足場の上に乗っている場合がまさにこれ）。

### 3.5 圧殺

Solid（閉じるゲート）と壁の間に挟まれた Actor は「圧殺」とし、そのプレイヤーだけスポーン地点に復帰させる。ステージ全体のリセットにはしない（理不尽さを避ける）。

### 3.6 チューニング定数（`tuning.ts`）

単位は px / 秒。タイル = 24px、プレイヤー = 20w × 24h。

| 定数 | 値 | 意図 |
| --- | --- | --- |
| `GRAVITY` | 2000 | |
| `MAX_FALL` | 700 | |
| `RUN_SPEED` | 160 | 約 6.7 タイル/秒 |
| `RUN_ACCEL` | 1200 | |
| `GROUND_FRICTION` | 1600 | |
| `AIR_FRICTION` | 400 | 空中でも多少は制御できる |
| `JUMP_VELOCITY` | 500 | |
| `JUMP_CUT_MUL` | 0.4 | ボタンを離すと上昇を減衰＝可変ジャンプ |
| `COYOTE_TIME` | 0.08 | 崖から落ちた直後もジャンプ可 |
| `JUMP_BUFFER` | 0.10 | 着地直前の入力を拾う |

**この数値が設計上の意味を持つ**:

- 単独ジャンプの到達高 = `JUMP_VELOCITY² / (2 × GRAVITY)` = **62.5px ≒ 2.6 タイル**
- 相手の頭（+24px = 1タイル）に乗ってからのジャンプ = **86.5px ≒ 3.6 タイル**

よって **高さ3タイルの段差は「単独では絶対に無理／2人なら余裕を持って届く」** 境界になる。ステージ1はこの境界の上に成立している。ここを変えるとステージ設計が破綻するので、変更時は §7 の検算も併せて更新すること。

## 4. シグナルシステム（拡張性の中核）

ギミック同士を直接参照させると、「板を押したら扉が開く」ために板が扉を知る必要が生じ、組み合わせが増えるたびに配線が爆発する。これを **名前付きチャンネル** で完全に分離する。

```ts
class SignalBus {
  private channels = new Map<string, number>();
  set(name: string, value: number | boolean): void;
  get(name: string): number;            // 未定義は 0
  isOn(name: string): boolean;          // != 0
  clearFrame(): void;                   // 毎ステップ先頭で「瞬間型」をリセット
}
```

- **発信側**（感圧板、レバー、スイッチ）は自分が知っているチャンネル名に値を書くだけ。受信側の存在を知らない。
- **受信側**（ゲート、リフト、消える床）はチャンネル名のリストと結合モードだけを持つ。発信側の種類を知らない。

結合モードは式パーサを作らず、以下の3つで十分:

| mode | 意味 |
| --- | --- |
| `all` | 全チャンネルが ON（デフォルト） |
| `any` | いずれかが ON |
| `none` | すべて OFF（＝反転ゲート） |

これにより **「新しいスイッチ」を作っても既存の全受信側が自動的に対応し、「新しい受信ギミック」を作っても既存の全スイッチが自動的に使える**。組み合わせ爆発が起きない。

`latch: true` オプションを受信側に持たせると、一度 ON になったら戻らない（PoC では未使用だが、鍵付き扉などで効く）。

## 5. ギミックのインターフェース

### 5.1 定義

必須メソッドを最小にし、能力はオプショナルメソッドで表明する（Capability 方式）。実装しなければそのコストは一切かからない。

```ts
export interface GimmickContext {
  signals: SignalBus;
  stage: Stage;
  players: Player[];
  solids: SolidBody[];                // 前ステップ確定のギミック由来 Solid（閉じたゲート等）。ボールが地形と同様に読む
  requestClear(): void;              // ゴールが呼ぶ
}

export interface Gimmick {
  readonly type: string;
  readonly aabb: AABB;               // 判定・描画の基準矩形

  update(dt: number, ctx: GimmickContext): void;
  draw(r: Renderer): void;

  /** 実装すると Solid になる。null を返す間はすり抜ける（開いたゲート） */
  solidAABB?(): AABB | null;
  /** 実装すると重なり検知が来る（感圧板、鍵、ゴール、トゲ） */
  onOverlap?(player: Player, ctx: GimmickContext): void;
  /** 実装すると、返した矩形が追従カメラの対象に加わる（飛んでいるボールが先の地形を偵察する） */
  cameraTarget?(): AABB | null;
  /** ステージリセット時の初期化 */
  reset?(): void;
}

export interface GimmickDef<P = any> {
  type: string;
  create(params: P & { x: number; y: number }, stage: Stage): Gimmick;
}
```

ギミックが Actor を提供することもできる（箱）。`actor?(): Actor | null` を実装すると
物理世界に参加し、押し合いと「上に乗る」は §3.3 / §3.4 の既存経路がそのまま効く。
プレイヤー専用に書いたコードが、そのまま人以外にも使える形になっている。

重なり通知 `onOverlap` はプレイヤー限定ではなく `OverlapSource`（`box` と `isPlayer`）を
受け取る。感圧板は重さしか見ないので誰でもよく、鍵は `isPlayer` を見て人限定にする。
この線引きが World 3 の「道具が人の代わりをする」を成立させている。

### 5.2 登録簿

```ts
// registry.ts
const defs = new Map<string, GimmickDef>();
export function registerGimmick(def: GimmickDef) { defs.set(def.type, def); }
export function createGimmick(type: string, params: any, stage: Stage): Gimmick {
  const def = defs.get(type);
  if (!def) throw new Error(`未登録のギミック type: "${type}"`);
  return def.create(params, stage);
}
```

```ts
// gimmicks/index.ts —— ギミックを追加したらここに1行足すだけ
import { plateDef } from "./plate";
import { gateDef } from "./gate";
import { keyDef } from "./key";
import { goalDef } from "./goal";

[plateDef, gateDef, keyDef, goalDef].forEach(registerGimmick);
```

未登録の type を含む JSON は**ロード時に即エラー**にする（プレイ中に静かに消えるより、開発時に気付ける方がよい）。

### 5.3 更新順序（1ステップの処理順）

順序が曖昧だと、シグナルが受信側に届かないバグの温床になる。以下に固定する。

1. 入力サンプリング
2. プレイヤーの速度更新（重力・加速・ジャンプ）
3. ギミック `update()` — Solid の開閉・移動と**受信側の評価**はここ
4. ギミック由来の Solid 集合を物理へ反映
5. プレイヤーの `moveX()` → `moveY()`（ライダー搬送はこの中で完結）、接地・圧殺判定
6. **`signals.clearFrame()`**
7. 重なり判定 → 該当ギミックの `onOverlap()`（**感圧板がシグナルを立てるのはここ**）

**`clearFrame()` の位置が最重要**。これをステップ先頭に置くと、前ステップの手順7で発信側が立てた値を、受信側（手順3）が読む前に消してしまい、**感圧板の信号がゲートに一度も届かない**。実装初回にこの順序を誤って踏み抜いたので、変更するときは `tests/stage01.test.ts` の「板に乗るとゲートの Solid が消え、降りると戻る」で必ず検証すること。

この順序では、板を踏んでから扉が通れるようになるまで 1 フレーム（16ms）の遅れが出る。知覚できない差であり、扉が開いた瞬間にプレイヤーが押し出されて挟まる事故が起きない利点の方が大きい。

## 6. キャラクター表現（Clawd）

### 6.1 方針

Clawd の公式アセットは手元にないため、**Anthropic のクレイオレンジ `#D97757` を基調に、Clawd 的なシルエットをコードで描く**。ドット絵ではなくベクタ（`ctx.arc` / `quadraticCurveTo`）で描くので、拡大しても滑らか。

差し替えを前提にインターフェースを切る:

```ts
export interface CharacterSkin {
  draw(r: Renderer, s: CharacterState): void;
}
export interface CharacterState {
  x: number; y: number; w: number; h: number;
  facing: 1 | -1;
  vx: number; vy: number;
  grounded: boolean;
  squash: number;     // 1 = 通常, <1 = 潰れ, >1 = 伸び
  carrying: boolean;  // 頭に誰か乗っている
  color: PlayerPalette;
}
```

`ClawdSkin implements CharacterSkin` として実装。将来スプライトシートを使う場合は `SpriteSkin` を作って差し替えるだけで、ゲームロジックは無変更。

### 6.2 見た目の要素

- 丸みのあるずんぐりした胴体。上部に短いアンテナ/触角が1本。
- 目は大きめの単純なドット2つ。進行方向（`facing`）に寄せる。
- **スカッシュ＆ストレッチ**: ジャンプ踏切で縦に伸び、着地で横に潰れる。`squash` は着地時に 0.7 へ落として毎ステップ 1.0 へ指数回復させる。この1要素だけで「生きている感じ」が跳ね上がるので PoC でも省かない。
- **表情の変化**: 空中では目を少し大きく、頭に相手が乗っている（`carrying`）ときは踏ん張った目にする。協力ゲームなので「乗せられている」ことが一目で分かるのが重要。
- 接地時のわずかな上下バウンス（呼吸）。

### 6.3 2人の識別

P1 = クレイオレンジ `#D97757`、P2 = 同じ形で色相をずらした青緑 `#57A8D9`。形は完全に同じ Clawd で、色だけが違う。足元に自機カラーの小さな影を落として、重なったときも判別できるようにする。

### 6.4 パレット

## 7. ステージ1「Boost & Hold」

### 7.1 教えたいこと

1. **相手の頭に乗れば届く**（単独では絶対に届かない段差）
2. **片方が留まって、片方が進む**（感圧板とゲート＝役割の非対称性）
3. **役割は入れ替わる**（乗せた側が最後に自力で合流する）

「2人いないとクリア不能」であることが PoC の証明対象なので、単独攻略ルートが存在しないことを設計と数値の両方で保証する。

### 7.2 レイアウト

40 × 18 タイル。`#` = 壁、`.` = 空。

```

y=2   #......................................#
y=3   #......................................#
y=4   #......................................#
y=5   #......................................#
y=6   #......................................#
y=7   #......................................#
y=8   #......................................#
y=9   #......................................#
y=10  #......................................#

y=14  #......................................#

```

- 地面 = y=16 の上面（`y_px = 384`）
- **棚 + 仕切り壁** = x=13〜18 の y=13（`y_px = 312`、地面から **3タイル = 72px**）
- ゲート（ギミック）が x=18 の y=14〜15 を塞ぐ。閉じている間、地上からエリアAとBは行き来できない
- 棚の上（y=13 の上面）は x=13 から x=18 まで連続しており、**x=18 から右に歩けばエリアBへ落ちられる**

エリアA = x=1〜17（スタート地点）、エリアB = x=19〜38（鍵とゴール）。

### 7.3 配置

| 要素 | 位置（タイル） | パラメータ |
| --- | --- | --- |
| P1 スポーン | (4, 15) | |
| P2 スポーン | (7, 15) | |
| 感圧板 `plate` | (15, 12) w=2 | `emit: "sw1"` |
| ゲート `gate` | (18, 14) h=2 | `listen: ["sw1"], mode: "all"` |
| 鍵 `key` | (25, 15) | `id: "key1"` |
| ゴール `goal` | (35, 15) w=3 | `requires: ["key1"], needAllPlayers: true` |

### 7.4 想定解法

1. P1 が棚の左下（x≈12）に立つ。P2 が P1 の頭に飛び乗る。
2. P2 が頭の上からジャンプして棚（y=13）に上がる。
3. P2 が棚の上の感圧板 (15,12) に乗る → `sw1` が ON → x=18 のゲートが開く。
4. P1 が地上を右に歩き、開いたゲートを抜けてエリアBへ。
5. P2 が板から降りる（ゲートは閉じるが、P1 はもう向こう側）。P2 は棚を右端まで歩き、x=18 から**エリアBへ落下**して合流。
6. P1 が鍵 (25,15) を回収。
7. 2人ともゴール (35〜37, 15) に入る → クリア。

### 7.5 単独攻略が不可能であることの検算

| 経路 | 必要高さ | 単独の到達 | 判定 |
| --- | --- | --- | --- |
| 地上から棚 (y=13) に登る | 72px（3タイル） | 62.5px | **不可**（9.5px 不足） |
| 地上から仕切り壁 x=18 を越える | 72px | 62.5px | **不可** |
| 頭に乗ってから棚に登る | 72px | 24 + 62.5 = 86.5px | 可（14.5px 余裕） |
| 頭に乗った位置から棚まで | 48px | 62.5px | 可 |

単独では棚にも仕切り壁にも登れず、ゲートを開ける感圧板は棚の上にしかない。**エリアBへ到達する経路が物理的に存在しない**。

余裕 14.5px は「シビアすぎず、しかし偶然できてしまうこともない」量。`JUMP_VELOCITY` を変更する場合はこの表を再計算すること。

### 7.6 失敗と復帰

- 手順3〜5の順序を間違えると（P2 が板に乗らずに先へ落ちる）、P1 が取り残されて詰む。**これは意図した失敗**で、協力の必要性を体感させる。
- `R` キーで即リセット。詰み検出は実装しない（プレイヤーが自分で気付いて押す方が学習になり、実装も単純）。

### 7.8 ワールド1「スイッチ（押している間だけ効く）」

ステージを1本ずつではなく、**1つの学習テーマ = 1ワールド**でまとめる（Pico Park 本家の構成に倣う）。ワールド1のテーマは「スイッチは押している間だけ効く」。4ステージで、このテーマの異なる側面を1つずつ教える。

| ステージ | 名前 | 教える側面 |
| --- | --- | --- |
| 1-1 | Boost & Hold | 相手の頭に乗れば届く／片方が留まり片方が進む（§7 で詳説済み） |
| 1-2 | Both at Once | **2枚のスイッチを同時に**押さないと開かない＝両者とも同時に別の場所を占有するので、開いた瞬間だけ自由になる。だからゲートは `latch: true` で開いたら戻らない必要がある |
| 1-3 | Bridge | スイッチが「開ける」のではなく**閉じたときだけ通れる床**を作る（`mode: "none"` の反転ゲート）。1-1・1-2とは逆に「押されている間だけ実体化する」経験をさせ、2枚の板を**役割交代でリレー**する |
| 1-4 | Two Keys | 1-1〜1-3の総仕上げ。**橋を架けた人はその橋を渡れない**（`latch` 付きゲートを対岸の同時押しで開け、持ち手を交代する）のと、**入口と出口が逆位相**（同じチャンネルの反転ゲートと通常ゲートで部屋の出入りを役割交代させる）という2つの洞察を1本に同居させる（§7.11 で詳説） |

4ステージとも既存ギミック（`plate` / `gate` / `key` / `goal`）の組み合わせだけで作られており、ギミックのコードは1行も追加していない（§8.2 の想定どおり）。

ワールドは現状1つしかないため、`StageData` に `world` フィールドはまだ足していない。ステージ番号の「1-」部分は `game.ts` の HUD 描画側で固定値として持たせている。第2ワールドを作るときに `StageData` へ `world: number` を追加し、そちらから取るように直す。

### 7.9 ステージ1-2「Both at Once」の検算

`src/stages/stage-02.json`。レイアウトはステージ1と同じ 40×18 タイルで、地面（y_px=384）の右手前（タイル28）に、床から天井まで完全に塞ぐ縦の壁＋ゲートがある。棚（タイル17〜22, y=13, 地面から3タイル=72px）はステージ1と同じ理由で単独では登れない。

| 要素 | 位置 | 役割 |
| --- | --- | --- |
| 板A `swA` | 地上 (4, 15) | 地上に残った側が踏む |
| 板B `swB` | 棚の上 (19, 12) | ブーストされた側が踏む |
| ゲート | (28, 14) h=2, `listen: ["swA","swB"]`, `mode: "all"`, `latch: true` | 縦の壁（列28, 行1〜13が地形として常時Solid）＋ゲート（行14〜15）で床から天井まで塞ぐ |

**単独攻略が不可能であることの検算**:

| 経路 | 必要高さ / 条件 | 単独の到達 | 判定 |
| --- | --- | --- | --- |
| 地上から棚 (y=13) へ登る | 72px（3タイル） | 62.5px | **不可**（9.5px不足） |
| 板Aと板Bを同時に踏む | 2箇所を同時に占有 | 1人は1箇所にしか居られない | **不可**（棚に登れる／登れないに関係なく、そもそも1人では成立しない条件） |

棚に登れないので板Bへ単独で到達できず、たとえ登れたとしても板Aと板Bを同時に踏むことは1人の体では不可能。**`mode: "all"` の2チャンネル同時条件が、この不可能性の核**。

**`latch: true` が必須である理由**: 両方を同時に踏めるのは「地上の1人」と「棚の1人」が別々に配置されているこの一瞬だけで、ゲートが開いた次の瞬間には少なくとも片方が板から離れて移動を始める（でないとゴールへ辿り着けない）。`latch` が無ければ、板から足が離れた時点でゲートが再び閉じ、抜けている途中のプレイヤーを挟んでしまう。ステージ1のゲートは `latch` 不使用（板の上から動かないので閉じても困らない）だが、このステージでは`latch`が無いと物理的にクリア不能になる。`tests/stage02.test.ts` の「ラッチ」テストで固定している。

### 7.10 ステージ1-3「Bridge」の検算

`src/stages/stage-03.json`。40×18タイル、床面はどこも y=13（y_px=312）で統一されている１部屋。中央のタイル18〜23（幅6タイル=144px）だけ床が無い谷で、その下はグリッド外＝谷底（y_px=432、床面から120px＝5タイル）まで落ちる。

| 要素 | 位置 | 役割 |
| --- | --- | --- |
| 板1 | (12, 12) | 谷の手前側（近い方） |
| 板2 | (26, 12) | 谷の対岸側（遠い方） |
| 橋（ゲート） | (18, 13) w=6 h=1, `listen: ["sw1"]`, `mode: "none"` | 板1・板2は**同じチャンネル `sw1`** を鳴らす。反転ゲートなので、押されているあいだ**閉じる＝橋として実体化する** |

**単独攻略が不可能であることの検算**:

| 経路 | 必要距離 / 高さ | 単独の到達 | 判定 |
| --- | --- | --- | --- |
| 谷を跳び越える | 144px（6タイル） | 最大水平到達距離 約87px（3.63タイル） | **不可**（約57px不足） |
| 谷底から地上へ登り返す | 120px（5タイル） | 単独62.5px／頭に乗っても86.5px | **不可**（頭に乗っても33.5px不足） |

跳躍では届かず、誤って落ちても登り返せない（しかも登り返すには落ちた側にもう1人が要るが、そもそもここに来られるのは2人揃っている場合だけ）。橋を実体化させるには常にどちらかの板の上に誰かがいなければならないので、**2人が近い板／遠い板を交代で踏みながら渡るリレー**以外にクリア経路が無い。`tests/stage03.test.ts` の「谷は単独では渡れない」「受け渡しで渡れる」で固定している。

板1・板2が別チャンネルではなく**同じ `sw1`** を共有している点が肝で、これにより「Aが手前で踏み続ける→Bが渡る→Bが対岸の板に乗り換える→Aが渡る」という**受け渡し**が可能になる（別チャンネルにして `mode: "any"` にしても橋の開閉自体は同じ結果になるが、「どちらの板でも同じ橋が出る」という設計意図を1チャンネルの方が素直に表せるため、こちらを採用している）。

### 7.11 ステージ1-4「Two Keys」の検算

`src/stages/stage-10.json`（ID の番号と表示ラベルは無関係。§8.2 のとおり配列順と `world` フィールドだけがラベルを決めるので、`stage-04` は既に World 2「Ferry」が使っている関係で、空いている ID `stage-10` を使い、`stages/index.ts` 側で `stage-03` の直後・`stage-04` の直前に挿入している）。1-1〜1-3の3本より難度を上げた、ワールド1の総仕上げステージ。操作量はおよそ倍、鍵は2つ、そして**2つの異なる洞察**を1本のステージに同居させている。

**この設計は高さによる詰みを一切使わない。** World 3 の設計記録（§7.19, §7.20）で、相方の頭に乗った状態で頭側がジャンプする「二段ジャンプ」が地面から149px届き、箱を使ったどんな段差の見積もり（3-2 の110.5px、3-3 の173pxでも実操作では成立しない）も上回ってしまうことが分かっている。つまり**このエンジンで高さによる「単独では届かない」を保証する設計は信頼できない**。1-4 は床が全域フラットで、難度は「幅（渓谷）」と「信号の位相（部屋の出入り）」という**要求の形**だけで作っている。

#### 洞察1: 「橋を架けた人はその橋を渡れない」

40×18タイル、地面は全域 y=13（`y_px=312`）で統一。渓谷はタイル10〜14（幅5タイル=120px、深さも120px＝グリッド下端まで）。板α (6,12) が渓谷にかかる橋（`mode:"none"` の反転ゲート、`listen:["swA"]`）を実体化させる。橋を渡った先（対岸、タイル15〜19）に板β (15,12, `emit:"swB"`) と、**橋と同じチャンネル `swA` を鳴らす板α2** (18,12) がある。橋の先のラッチゲート（列20、`listen:["swA","swB"], mode:"all", latch:true`）は α と β の**同時押し**でしか開かない。

| 項目 | 数値 | 判定 |
| --- | --- | --- |
| 渓谷の幅 | 120px（5タイル） | 最大水平到達距離 約87px を超え、**跳躍不能** |
| 渓谷の深さ | 120px（グリッド下端まで） | 単独62.5px／頭に乗っても86.5px、**登り返し不能** |
| 橋の範囲 | x=240〜360, 上面 y=312 | 渓谷幅ぴったり、地面と面一（段差なし） |
| 板β・板α2の位置 | x=360〜408 / x=432〜480 | ともに対岸（タイル15以降）＝橋を渡らないと踏めない |

橋は板αを踏んでいる間しか実体化しない。板αとβを同時に踏まないとラッチゲートは開かないが、βは対岸にしかない。**板αを踏んだままの人は対岸へ渡れない**ので、単独ではラッチゲートを開けられない。想定解法は、P1が板αを踏み続けてP2を対岸へ渡す→P2が板β(同時押し)でラッチを開ける→P2が同じ`swA`の板α2に乗り換える（橋の維持役を引き継ぐ）→P1が板αを離れて渓谷を渡り、開いたラッチゲートを抜けて合流する、という**受け渡し**。`tests/stage10.test.ts` の「橋（反転ゲート）の開閉」「ラッチゲート」ブロックで各条件を、「想定手順で2人ともゴールに到達できる」で受け渡し全体の通しクリアを固定している。

#### 洞察2: 「入口と出口が逆位相」

鍵2は列27〜32に挟まれた密室にある。入口ゲート（列27、`listen:["swC"], mode:"none"`）は**誰もswCを押していないときだけ**通れる反転ゲート。出口ゲート（列32、`listen:["swC"], mode:"all"`）は**押しているときだけ**通れる通常ゲート。どちらも同じチャンネル `swC` を聞く。部屋の外、入口の手前に板γ (24,12)、出口の先に板δ (34,12) があり、どちらも `swC` を鳴らす。

| 項目 | 状態 | 入口 | 出口 |
| --- | --- | --- | --- |
| 誰もswCを押していない | 初期状態 | 通れる（非Solid） | 塞がれる（Solid） |
| 誰かがswCを押している(γまたはδ) | 板を踏んでいる間 | 塞がれる（Solid） | 通れる（非Solid） |

単独では「部屋に入る」と「部屋から出す」を同時に満たせない。誰かが部屋の外（γかδ）で板を押さえないと出口は開かないが、押さえている本人は当然部屋の中にいない。想定解法は、P2が誰も押していないうちに入口から入って鍵2を取る→P1が板γを踏む（入口が閉じ、出口が開く）→P2が出口から出る→P1が板γを離れる（入口が再び開く）→P1が入口から入る→P2が板δを踏む（出口が再び開く）→P1が出口から出る、という**役割交代**。2人とも部屋の外（板δの先）へ抜けないとゴールに到達できないので、この往復は省略できない。`tests/stage10.test.ts` の「鍵2の部屋: 入口と出口は逆位相」ブロックで各位相の状態を、通しクリアのテストで役割交代の全手順を固定している。

#### ゴール

`goal` は `requires:["key1","key2"], needAllPlayers:true`。鍵1つだけ、あるいは2人のうち1人だけがゴール矩形に入っている状態ではクリアしない（`tests/stage10.test.ts` の「ゴールは両方の鍵と両プレイヤーを要求する」で固定）。

### 7.12 ワールド2「動く足場」

ワールド1が「スイッチは押している間だけ効く」だったのに対し、ワールド2のキーアイデアは **`platform`（動く足場）**。信号を `listen` すると「立っている間だけ終点へ、離すと始点へ戻る」動き方をする点はゲートと同じだが、足場は乗った Actor を運ぶ（SPEC §3.4）ぶん、単なる開閉より一段複雑な協力パターンを作れる。4ステージで、この足場の異なる側面を1つずつ教える。

| ステージ | 名前 | 教える側面 |
| --- | --- | --- |
| 2-1 | Ferry | 板を踏んでいる間だけ動く足場で、対岸へ渡す・戻す。両岸に板があるので「送った側」も後から自力で乗り込める |
| 2-2 | Counterweight | **1つの信号で2つの足場を逆向きに動かす**（つり合いおもり）。専用オプションは無く、`from`/`to` を入れ替えるだけで表現される（`platform.ts` のコメント参照）。同じチャンネルの板が両方の棚にあるので、途中で持ち手を交代できる |
| 2-3 | Tandem | `listen` の無い足場は**信号と無関係に常時往復し続ける**。谷を渡る手段はこれしか無く、タイミングの問題になる。対岸の高い棚は頭に乗ってのジャンプでしか届かず、もう1人を運ぶのは信号駆動のリフト（同じ `platform` を別のパラメータで使っているだけ） |
| 2-4 | Tower | 2-1〜2-3の総仕上げ。**足場は道のりの半分しか行かない**ので中段ですれ違う一瞬に乗り継ぐしかないのと、**上の板が乗っている島は、足場そのものが橋になっている**ので押した本人が取り残される、という2つの洞察を1本に同居させる。画面の上半分まで使う縦構成（§7.16 で詳説） |

4ステージとも既存ギミック（`plate` / `platform` / `key` / `goal`）の組み合わせだけで作られており、**`platform` 以外に新しいギミックのコードは1行も追加していない**（§8.2 の想定どおり）。ワールド1で使った `gate` / `key` はワールド2では使っていないが、これは「このワールドの主題に不要だから」であって、`platform` と併用できないわけではない。

逆位相（つり合いおもり）を実現する `mode` や `invert` のような専用オプションは `platform.ts` に存在しない。**`from`（start）と `to` を入れ替えて2つの足場を定義するだけ**で、同じ信号 `sw1` に対して片方は上昇、もう片方は下降する。これは SignalBus が発信側・受信側のどちらの種類も知らない疎結合設計（§4）の効果がそのまま表れた例で、「新しいギミック」を足さずに新しい振る舞いの組み合わせを作れることを示している。

### 7.13 ステージ2-1「Ferry」の検算

### 7.17 ワールド3「運べる箱」

ワールド1が「スイッチは押している間だけ効く」、ワールド2が「動く足場」だったのに対し、ワールド3のキーアイデアは **`crate`（押せる箱）＝道具が人の代わりをする**。箱そのものはほとんど自前のコードを持たず、押し合いと「上に乗る」はプレイヤー同士のために書いた Actor の経路（SPEC §3.3, §3.4）がそのまま効く。感圧板は重さしか見ないので、箱を載せれば「板に人が残り続けなければならない」問題への解答になる。3ステージで、この「道具が人の代わりをする」の異なる側面を1つずつ教える。

### 7.21 ワールド4「ブロック崩し」とステージ4-1「Breakout」

ワールド1〜3のキーアイデアが「スイッチ」「動く足場」「箱」だったのに対し、ワールド4は
**ボールが地形を壊す**。人がラケット（板）の役をするブロック崩しで、壊さないと進めず、
壊しすぎると進めない。まず 4-1 の1ステージから始め、厚い壁と縦の返球を 4-2（§7.22）で足した。

**新しく書いたコード**は2か所だけ。

- `Tile.Brick`（グリッド文字 `B`）。`TileGrid.isSolid()` が Brick を含むので、当たり判定・
  描画のハイライト・箱や足場との関係は Solid と全く同じ経路で動く。壊す＝`grid.set()` で
  Empty にするだけで、`TileGrid.reset()`（`Stage.reset()` から呼ぶ）がロード時の地形に戻す。
  つまり「地形が変わる」を、ギミックではなく地形そのものの責務にした。
- `ball`（`src/game/gimmicks/ball.ts`）。`GimmickContext` に既にある `grid` と、
  `onOverlap` で渡ってくる人だけで動くので、ギミックの共通面は増やしていない。

**ボールの規則**は3つで、どれも 4-1 の盤面に直接効いている。

| 当たった相手 | 起きること | 盤面での意味 |
| --- | --- | --- |
| 人 | 人の中心からボールの中心へ向かう向きに飛ぶ（止まっていれば打ち出し、飛んでいれば跳ね返り） | **線上に立っている人は誰でも板になる** |
| `B` | そのブロックが消え、入った軸の速度成分だけ反転する | 壁の根元と橋を壊す |
| `#` | 消えて 0.4 秒後に元の位置に戻る | **返さなければボールは止まる** |

壁で跳ね返らせないのは意図的で、跳ね返り続けるボールは放っておくだけで全部のブロックを
壊してしまい「壊しすぎ」を作れない。壁で消えるから、止めたい側は「返さない」だけでよい。

**レイアウト**（40×18、床の上面は行13＝312px）

| 要素 | 位置 | 役割 |
| --- | --- | --- |
| ボール | (2,12) | 左端。右側から触れると左の壁へ飛んで消えるだけ。**跳び越えて左側（1タイルの隙間）に回り込む**と右へ打てる |
| 壁 | x=18, 行1〜8 が `#`、行9〜12 が `B` | 天井まで塞ぐ。根元 (18,12) を壊すと1タイルの穴が開く |
| 谷 | x=26〜31、深さ120px | 幅144px は二段ジャンプの水平到達102pxを超える |
| 橋 | (26〜31, 12) の `B` 6個 | 床より1タイル高い。ボールと同じ行にある |
| ゴール | (35〜37, 12) | 両方の人が要る |

ボールの休憩位置・壁の根元・橋が**全部同じ行12**にあるのが設計の核で、床に立ったまま
打ち返し続けると、壁の次は橋が左から1個ずつ壊れる。

**気づき①「線上の人は板になる」** — 打った人から離れる向きに飛ぶので、右へ打つには左に
回り込む。相方がスポーン位置に立ったままだと、ボールは2人の間を往復して壁に届かない。
相方は跳んで通す（または頭に乗って線から外れる）。

**気づき②「壁を抜けたら返さない」** — 根元が壊れた後に戻ってくるボールを返すと、穴を抜けて
次に壊れるのは橋。2人とも跳んでやり過ごせば、ボールは左の壁で消えて元の位置に戻る。

**検算**（`tests/stage12.test.ts` で実測）

- 橋は床より1タイル高いので、左から k 個欠けると「k×24px の幅 ＋ 24px の段差」を跳ぶことになる。
  k=2（48px）は単独ジャンプで乗れ、k=3（72px）は乗れない。**余計に返してよいのは2回まで**。
- 壁は天井まで続くので、二段ジャンプで越える経路は無い。壁の高さの見積もりには依存していない。
- 谷は 144px で、二段ジャンプの水平到達 102px より広い。橋以外の渡り方は無い。
- `R` でやり直すと、壊したブロックも元に戻る（地形が `Stage.reset()` に含まれる）。

### 7.22 ステージ4-2「Chimney」

4-1 が「同じ列を1回打ち返せば貫通する」壁だったのに対し、4-2 は**厚い壁**（3列×4段の
ブロック）と**縦方向の返球**を持ち込む。新しいギミックのコードは無く、ボールの狙いの
計算だけを変更している。

**ボールの規則の変更（軸スナップ）**

| 変更点 | 内容 | 理由 |
| --- | --- | --- |
| 判定を比率から状態へ | 横のずれが縦のずれの半分未満なら、真下から（真上に）／真上から（真下に）飛ぶ。横からの接触は、地上に立つ人が返せば水平、空中の人が返せば必ず45°斜め上に飛ぶ | 旧ルールは中心のずれの比率だけで判定していたため、接触した瞬間の人の高さで角度が27°〜49°の間でぶれて狙えなかった。45°に固定すると幾何が決まり、「穴は自分の1.5タイル後ろに開く」のように立つ位置で狙える |
| 帰結 | 床置きのボールAは、立ったまま返せば水平専用。浮かせたボールBは、真下から突き上げると垂直専用 | 厚い壁は横から崩し、煙突は下から崩す、という2つの解法を両立できる（4-2 の設計自体は変わらない） |

想定ルート: トンネル（厚い壁）→ 階段 → 廊下を左へ → 穴を跳び越える → 橋を渡る → ゴール。

**気づき①「同じ列を3回返す」** — 4-1 の壁は1回で抜けたが、4-2 の壁は行9〜12全部を
`B` で塞いだ3列の厚みがある。床に立ったまま(=水平にしか飛ばない)、同じ行12を3回
打ち返して初めて貫通する。上や下へ回り込む経路は無い。

**気づき②「浮いたボールは真下から打つ」** — ボールBは (27,10) に浮いている。x=27 の真下に
立ってジャンプで下から当てると垂直に飛び、廊下の穴 (27,8) を抜けて煙突の最下段 (27,7) を壊して
跳ね返る。落ちてきたボールは、真下に立ったままの人がまた真上へ返すので、**一度打てば縦のラリーが
勝手に続き**、煙突は根元から1個ずつ崩れて約9秒で全部消える。最後は天井の `#` に当たって消え、
(27,10) へ戻る。廊下を通るのに要るのは (27,7) の1個だけで、その後は穴 (27,8) を跳び越える。
中心が 12px ずれて当てると斜めに飛んで廊下の床で消え、煙突は無傷（`tests/stage13.test.ts`）。

**気づき③「斜めに返すと橋が減る」** — ボールAをジャンプ中(中心がずれた状態)に返すと軸スナップ
により斜め上に飛び、廊下の橋 (10〜15,8) を下から壊してしまう。橋は6タイルあるので数個
減ってもすぐには詰まないが、壊しすぎるとゴール直前の足場を失う。「狙いが軸に揃う」のは
オフセットの小さい成分を切り捨てるだけなので、**斜めそのものは消えていない**ことに注意。

### 7.23 ステージ4-3「Door」

4-1・4-2 は1画面に収まっていたが、4-3 は 80×18 とワールド4で最初の**画面より広い**ステージで、
初めて追従カメラ (§1.2) が仕事をする。新しく足したのはギミックの機能2つで、盤面の要素
（ボール・板・ゲート）自体は既存のものをそのまま使っている。

**新しい土台**

| 追加 | 内容 | 理由 |
| --- | --- | --- |
| `cameraTarget?(): AABB \| null`（`Gimmick`、§5.1） | 飛んでいる間だけ自分の矩形を返す。ボール (`src/game/gimmicks/ball.ts`) が実装する | カメラが人だけでなく飛んでいるボールも囲むようになり、**打った球が先の地形を偵察する**。壁の3回目のヒットで scale 0.98、橋に達する頃には 0.72 まで引き、消えると 1.0 に戻る（実測） |

### 7.24 ステージ4-4「Skylight」

4-4 は再びボールの狙いの計算を変える。§7.22 で入れた「軸スナップ」（中心のずれの比率で
水平・垂直・斜め45°を選ぶ方式）をやめ、**状態**（地上か空中か）で狙いを決める方式に
置き換えた。あわせて、箱 (`crate`) に当たった飛んでいる球も壁と同じく消えるようにした
（従来は素通りしていた）。

**規則の変更**

| 変更点 | 内容 | 理由 |
| --- | --- | --- |
| 判定を比率から状態へ | 横のずれが縦のずれの半分未満なら真下(上)から＝真上(真下)に飛ぶ。横からの接触は、地上に立つ人が返せば水平、空中の人が返せば必ず45°斜め上に飛ぶ | 旧ルールは接触した瞬間の人の高さで角度が27°〜49°の間でぶれて狙えなかった。45°に固定すると幾何が決まり、「穴は自分の1.5タイル後ろに開く」のように立つ位置で狙える |
| 箱もボールを止める | 飛んでいる球が箱に当たると、壁と同じく消える（従来は素通り） | 箱は人が乗れる足場なので、球にとっても壁と同じ扱いにするのが一貫している。4-4 では箱を球の通り道の下（行12）で運ぶが、球は頭の高さ（行11）を飛ぶので当たらない |
